# Markdown conventions

Правила ниже нужны, чтобы README и `docs/` одинаково проходили Prettier,
markdownlint, ESLint Markdown и `npm run check:docs`.

## Длина строки и структура

- Максимум 120 символов в строке, включая заголовки и таблицы.
- Один заголовок H1 в начале файла.
- Не пропускайте уровни заголовков.
- Вокруг заголовков, списков, таблиц и fenced blocks оставляйте пустую строку.
- Файл заканчивается одним переводом строки.
- Длинные URL лучше выносить в reference links в конец файла.

## Fenced code blocks

- Всегда указывайте язык: `bash`, `ts`, `tsx`, `json`, `yaml` или `text`.
- Для JSX используйте `tsx`, а не `typescript`.
- Не вставляйте неполные фрагменты как исполняемый код, если ESLint должен их
  проверить. Для псевдокода используйте `text`.
- Команды должны быть копируемыми без символа `$` в начале строки.

Пример:

```bash
npm run lint:md
npm run check:docs
```

## Ссылки на скрипты и пути

`scripts/check-docs.ts` автоматически проверяет:

- каждая команда запуска npm-скрипта должна соответствовать реальному script в `package.json`;
- inline-code пути с префиксами `docs/`, `.idea/`, `scripts/`, `.husky/`,
  `tools/eslint/`, `src/` и `tests/` должны существовать;
- относительные markdown-ссылки должны вести на существующий файл;
- маркеры версии Node.js должны совпадать с минимумом `engines.node`;
- в README должен быть хотя бы один маркер минимальной версии Node.js.

Проверка не применяется к `artifacts/`: там лежит сгенерированная схема и
исторический отчёт об аудите со ссылками на пути того коммита, который он описывает.

Не пишите выдуманный путь в backticks как пример. Если путь иллюстративный,
используйте обычную прозу или шаблон с `*`, который проверка сознательно пропускает.

## Таблицы

- Используйте aligned style: Prettier выравнивает разделители и колонки.
- Держите ячейки короткими; длинное объяснение выносите в абзац после таблицы.
- Не используйте HTML внутри таблиц без необходимости.
- Заголовки колонок должны быть существительными или короткими фразами.

## Символы

- Стрелка в прозе и схемах: ASCII `->`, а не Unicode arrow.
- Многоточие: три ASCII точки `...`.
- Не используйте emoji и Unicode box/line drawing graphics.
- Для статусов в служебных отчетах используйте `[OK]`, `[FAIL]`, `[TODO]`,
  `[WARNING]` и `[INFO]`.
- Русская типографика в обычном тексте допустима, если не нарушает машинную
  unicode-policy.

## Чеклист перед коммитом

```bash
npm run lint:md
npm run check:docs
npm run format:check
```

Если правили только документацию, этих трех команд достаточно для локальной
проверки. Husky дополнительно запустит Prettier и markdownlint для staged `.md`.
